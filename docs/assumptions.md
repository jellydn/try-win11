# Assumption validation

Reviewed: 2026-10-19. This is a source review, not hardware validation or legal advice. Linked pages can change. Pin actual artifacts during milestone 1; never infer a tested version from a documentation URL.

## Evidence register

| Area | Finding and evidence | Consequence / required validation |
| --- | --- | --- |
| QEMU + HVF | QEMU documents `host` CPU support with HVF on its ARM `virt` board [S2]. UTM documents Windows virtualization and installation [S3]. | Strong feasibility evidence, not proof that an arbitrary stock QEMU/firmware pair works. M1 must reproduce without relying on an installed UTM app. Identify any UTM patches needed. Fail rather than silently use TCG. |
| Virtualization.framework | Apple describes macOS and Linux guests [S1]. Its documentation does not establish a supported Windows guest path. Generic EFI support alone does not supply Windows-compatible devices, TPM, or drivers. | Do not use VZ for the initial runtime. This is not a claim that Windows can never boot on VZ. Reconsider only with an end-to-end documented and tested Windows path. |
| Media | Microsoft's public ARM64 ISO page explicitly describes VM use on supported hardware, multi-edition media, SHA-256 verification, and 24-hour download links [S4]. | User downloads from Microsoft and imports the ISO first. Reject AMD64 media. Record exact Windows build, edition, language, ISO hash, and publisher hash source. No scraped permanent URL, prebuilt Windows disk, Insider dependency, or UUP reconstruction needed. |
| Licensing / support | Microsoft names Parallels as an authorized solution in the cited Mac support article; it requires a separate Pro license per instance and says Pro keys are architecture-agnostic [S5]. It does not name Try Win11 or QEMU. | Public ISO availability and activation do not prove support or grant redistribution rights. Review current retail/volume terms for the chosen edition and use. Obtain qualified licensing advice before public distribution or automated download. Do not transfer an OEM license by assumption. |
| Windows requirements | Microsoft lists 2+ cores, 4 GB RAM, 64 GB storage, UEFI Secure Boot capability, TPM 2.0, and DX12/WDDM 2.0 graphics [S6]. Its VM section contains Hyper-V-specific terminology, not a QEMU certification. | Allocate above minima; turn Secure Boot on as a project requirement. A setup pass with a basic display does not prove all Windows requirements or supported-hardware status. Record graphics/CPU compliance gaps explicitly. |
| UEFI | TianoCore provides an AARCH64 QEMU firmware build path and a TPM2 build option [S7]. UTM documents UEFI, TPM and Secure Boot key preloading [S8]. | Need AArch64 EDK II firmware, not x86 OVMF copied from a tutorial. Validate ACPI, flash layout, persistent variables, TPM measurements, and key enrollment as one stack. A firmware filename containing `secure` is not evidence of active Secure Boot. |
| TPM 2.0 | QEMU documents the ARM `tpm-tis-device` frontend and emulator backend [S9]. swtpm supplies a libtpms-based software TPM with socket interfaces [S10]. UTM warns the host can read its secrets [S8]. | Build/package swtpm + libtpms for macOS ARM64 and prove Windows detection. ARM TPM ACPI/PPI behavior varies with version. Do not copy the docs' Linux KVM/`acpi=off` example into a Windows HVF recipe. The virtual TPM is not Apple's Secure Enclave or a physical TPM passthrough. |
| Secure Boot | UTM documents Microsoft KEK/db plus platform-key enrollment and a variables reset process [S8]. | Need correct firmware verification support, PK/KEK/db/dbx and current Microsoft boot certificates. Keep Windows driver-signature checks on. Verify enabled state and unsigned EFI rejection. Plan revocation/certificate updates; never reset an existing VM's variables to fix a boot error without consent. |
| ARM64 drivers | Microsoft says kernel drivers must be native ARM64; x86/x64 user-app emulation does not apply to drivers [S11]. UTM documents an ARM64 guest-tools path [S12]. | Audit each selected driver binary, INF hardware ID, catalog signature, version and license. Do not assume a generic virtio-win ISO contains usable signed ARM64 drivers for every device. Test with Secure Boot and normal code integrity enabled. |
| Display / graphics | QEMU `virt` has no default display [S2]. UTM 5 documents experimental DX11 via DXMT and DX12 via D3DMetal when available, with limited games compatibility and a Rosetta dependency for D3DMetal [S13]. Older UTM 4.1 advice saying no Windows 3D drivers exists [S14] but is not a current categorical limit. | Baseline: firmware framebuffer then a proven signed ARM64 display-only driver over a local console. Host Metal rendering does not imply guest DirectX acceleration. Do not promise gaming, DX12 compliance, GPU passthrough, or parity with Parallels. Audit experimental stack rights and stability separately. |
| Networking | QEMU user networking provides a NAT-style route without a host bridge [S15]. Guest NIC support is a separate driver problem. | Start libslirp user networking with no inbound forwarding. Validate NIC driver during Setup/OOBE, DNS, HTTPS, Windows Update, reconnect, VPN and host firewall behavior. NAT is not an isolation boundary against host/LAN access. Defer vmnet/bridging and their entitlement/privilege requirements. |
| Audio | QEMU supports device and backend selection [S15], but that does not establish a working Windows ARM64 audio driver. | Test an emulated USB audio device with Windows inbox class driver first, paired with one chosen CoreAudio or SPICE audio route. No AC97/HDA/virtio-sound assumption. Audio output is a beta gate; microphone is deferred. |
| Clipboard | UTM documents SPICE clipboard synchronization with guest tools [S16]. | Need working SPICE agent/channel and host pasteboard implementation, not QMP. Start explicit opt-in text only. Test both directions, Unicode, limits and disabled state. Avoid a new privileged guest service if existing tools work. |
| Shared folders | UTM documents Windows SPICE WebDAV support; it warns that VirtFS/9p Windows support is lacking [S16]. | Use an audited SPICE WebDAV path if the ARM64 service works. No VZ virtio-fs or 9p promise. Test path confinement, read-only enforcement, revocation, reconnect and file integrity. An ISO transfer fallback is not a writable shared folder. |
| Signing / notarization | Apple requires the hypervisor entitlement in the process using Hypervisor APIs [S17]. Notarization requires signed executables and Hardened Runtime [S18, S19]. | Sign QEMU, not just the Swift parent. Sign all bundled code/dependencies from inside out, verify rpaths, notarize and staple the distributable. Minimize entitlements; HVF does not by itself justify JIT exceptions. Prove a quarantined download runs on a clean Mac without Homebrew. |
| Distribution / open source | QEMU is GPLv2 with component-specific licenses [S20]. Runtime, firmware, tools and graphics dependencies have separate terms. | Propose direct Developer ID distribution, not an initial App Store commitment. Review exact build licenses and provide required corresponding source/build scripts/notices. A subprocess boundary is not a blanket license exemption. Do not bundle Microsoft media or D3DMetal merely because another app uses it. |

## What remains unproven

No Try Win11 runtime version, firmware image, driver set, audio route, display integration, macOS minimum, installation time, performance result, legal clearance, signing result, or notarization result is established. The product is feasible enough for a **bounded boot experiment**, not a full-product commitment. Failed licensing, secure boot, ARM64 driver, or display tests can stop the project or reduce its claims.

Primary platform and upstream sources are preferred. UTM documents its own integrated stack; its success does not certify a stock QEMU build. QEMU `master` documentation may describe unreleased features.
